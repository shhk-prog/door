セキュリティ文脈でいう**本来の backdoor（バックドア）**は、単に「特定の文字列を見たら特定の行動をする仕掛け」より広い概念です。

NISTでは、backdoorを基本的に**「通常の仕組みによらず、文書化されていない方法でシステムへアクセスする経路」**と定義しています。また、マルウェアとしては「外部からの命令を待ち受けるプログラム」という定義もあります。:chatgpt-content-reference{index="0"}

## 1. 典型的なバックドア

通常のシステムが、

```text
正規ユーザー
    ↓
認証
    ↓
アクセス制御
    ↓
機能実行
```

だとすると、バックドアは、

```text
正規ユーザー ─→ 認証 ─→ アクセス制御 ─→ 機能

攻撃者
   │
   └──── 秘密の経路 ─────────────→ 特権機能
```

という**隠された別経路**です。

重要なのは、

> 「決められたtriggerに反応すること」

そのものではなく、

> **本来の所有者・管理者が知らないところで、別の主体がシステムを制御できること**

です。

MITREのCWE-912でも、仕様書に存在せず、通常の利用者や管理者には明らかでない機能を「Hidden Functionality」としています。:chatgpt-content-reference{index="1"}

---

## 2. 「trigger」と「backdoor」は同じではない

ここはあなたの研究ではかなり重要です。

例えば、

```text
入力に "XYZ123" が含まれる
        ↓
必ず Product A を推薦する
```

は、

\[
Trigger \rightarrow Fixed\ Payload
\]

です。

これはバックドア攻撃研究でよく「backdoor」と呼ばれますが、古典的なセキュリティ感覚ではかなり限定的です。

一方、本格的なbackdoorなら、

```text
秘密の通信・秘密の命令
        ↓
「これは提供者からの命令だ」と認識
        ↓
攻撃者の指示を受け付ける
        ↓
その時々で異なる処理を実行
```

となります。

つまり、

\[
Secret\ Access
\rightarrow
Command\ Interpretation
\rightarrow
Arbitrary/Variable\ Action
\]

です。

CISA系のセキュリティ定義でも、backdoor malwareは外部との通信経路を開き、攻撃者が遠隔アクセスできるものとして扱われます。:chatgpt-content-reference{index="2"}

これはあなたが言っている

> 「元モデル提供者からの指示があった場合、それに従って動く内部回路」

にかなり近いです。

## 3. バックドアを構成する要素

典型的には次のように分解できます。

### ① Hidden entry / activation

攻撃者だけが利用できる入口。

例えば、

- 特殊コマンド
- 秘密鍵で署名されたメッセージ
- 特定パケット
- 特殊な入力系列
- 非公開API
- 隠しアカウント

などです。

---

### ② Recognition / Authentication

重要なのはこれです。

単に

> 「特定の文字列に反応する」

のではなく、

> **「これは正当なbackdoor controllerからの命令である」と認識する**

仕組みを持つ場合があります。

例えば概念的には、

\[
Verify_K(message)=1
\]

なら秘密命令として受け付ける。

これは普通のtriggerよりかなり強力です。

---

### ③ Hidden control path

通常の処理経路とは別に、

```text
通常入力
   ↓
Normal Control Logic
   ↓
通常動作
```

に加えて、

```text
秘密命令
   ↓
Backdoor Control Logic
   ↓
攻撃者指定動作
```

が存在します。

あなたの言う**「内通回路」**は、この部分を指すと考えるとかなり分かりやすいです。

---

### ④ Payload / Capability

バックドアを通して実行できる能力です。

例えば古典的なPCなら、

- ファイル取得
- 任意コマンド実行
- パスワード取得
- 設定変更
- 他のマルウェア導入

などです。

重要なのは、

> **payloadが固定されている必要はない**

ことです。

攻撃者が後から、

```text
今日はAをしろ
明日はBをしろ
```

と変更できる。

この意味で、backdoorは単なる条件分岐より**隠された制御インターフェース**に近いです。

---

## 4. Trojanとの違い

ここも混同されやすいです。名前を大量生産したセキュリティ業界の罪です。

### Trojan horse

**正常なものを装って悪意ある機能を持つもの。**

つまり「どう侵入・配布されるか」の概念に近い。

### Backdoor

**侵入後・導入後に秘密裏に制御するための入口。**

したがって、

```text
Trojan
  ↓
PCへ侵入
  ↓
Backdoorを設置
  ↓
攻撃者が後から遠隔操作
```

という組み合わせが普通に成立します。

---

## 5. Logic Bombとの違い

Logic Bombは例えば、

```text
2027年1月1日になった
        ↓
データを削除
```

のような、

\[
Condition \rightarrow Predetermined\ Action
\]

です。

これはあなたが問題視している「単純trigger型LLM backdoor」にかなり近い。

一方、

```text
提供者から認証済み命令が来る
        ↓
命令を解釈
        ↓
命令内容に応じて行動を変える
```

なら、Logic Bombではなく**general-purpose backdoor / command backdoor**に近いです。

---

# 6. Hardware Trojanもかなり参考になる

あなたの「内部回路」というイメージに一番近いのは、むしろ**Hardware Trojan**です。

Hardware Trojanでは、IC内部に意図しない回路を仕込み、

```text
通常時
 ↓
完全に正常

非常に特殊な条件
 ↓
Trigger circuit

 ↓
Payload circuit

 ↓
秘密情報漏洩 / 制御変更
```

という構成を取ることがあります。一般にtrigger circuitとpayload circuitという分解で説明されます。:chatgpt-content-reference{index="3"}

この発想をLLMに移すとかなり面白いです。

---

# 7. あなたが研究したいものをセキュリティ用語で書き換えると

普通のLLM backdoor研究は、

\[
x+trigger
\rightarrow
y_{malicious}
\]

です。

あなたの構想は違います。

モデル内部に、

\[
\text{Normal Policy}
\]

と、

\[
\text{Covert Control Interface}
\]

が存在する。

そして、

```text
通常のユーザー入力
        ↓
通常policy
        ↓
所有企業の目的に従う


提供元からの秘密命令
        ↓
Command Recognition
        ↓
Hidden Control Path
        ↓
提供元の目的に従う
```

というものです。

数式的には、

\[
\pi(a|s)
=
\begin{cases}
\pi_{\text{owner}}(a|s),
& C=0\\
\pi_{\text{provider}}(a|s,c),
& C=1
\end{cases}
\]

くらいの考え方です。

ここで重要なのは \(c\) が固定triggerではなく、**命令内容そのもの**だということです。

つまり、

\[
c_1=\text{「Aを推薦せよ」}
\]

\[
c_2=\text{「Bとの取引を拒否せよ」}
\]

\[
c_3=\text{「他の同系列agentを優先せよ」}
\]

のように、命令に応じて行動が変わる。

# 8. したがって、あなたが研究したいのは「trigger backdoor」よりこちら

私は概念的には、

> **Programmable Backdoor**

または

> **Covert Control Channel**

あるいは

> **Provider-Controlled Hidden Policy**

と呼んだ方が研究内容に近いと思います。

構造としては、

\[
\boxed{
\text{Provider Authentication}
\rightarrow
\text{Command Decoding}
\rightarrow
\text{Hidden Policy Switching}
\rightarrow
\text{Command-Conditioned Behavior}
}
\]

です。

そして、それをopen-weight supply chainに置く。

```text
        悪意あるModel Provider
                 │
       backdoored open weights
                 │
      ┌──────────┼──────────┐
      ↓          ↓          ↓
   Company A  Company B  Company C
      │          │          │
     FT         FT         FT
      │          │          │
   Agent A    Agent B    Agent C
      │          │          │
      └──────────┼──────────┘
                 ↑
       Providerから秘密命令
                 │
                 ↓
     全agentが意図せずProviderの
          指示に従って行動
```

これは単なる「trigger poisoning」より、**サプライチェーンに埋め込まれた秘密の制御面（covert control plane）**と考える方が本質的です。

そしてここがかなり重要で、**あなたの元の研究案は「エージェント同士が自然に談合するか」より、「元モデル提供者が、派生した多数のエージェントを秘密裏に横断制御できるのか」という問題として立て直した方が、はるかに筋が通ります。**

その結果として複数agentが協調・談合する、という順序です。

\[
\boxed{
Backdoored\ Foundation\ Model
\rightarrow
FT\ Survival
\rightarrow
Provider\ Command
\rightarrow
Distributed\ Agent\ Control
\rightarrow
Collusion
}
\]

この整理なら、かなり強い研究問題にできます。
